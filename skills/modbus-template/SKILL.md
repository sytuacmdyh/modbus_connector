# Modbus 设备模板

在用户指定的目标项目中分析实际协议，生成 Modbus Connector 的公共设备模板格式。
技能目录是工具资源所在位置，目标项目才是寄存器语义的来源；不要假定安装后还能访问
modbus_connector 仓库，也不要把目标项目路径硬编码为技能开发时的路径。

## 工作流程

1. 阅读目标项目的 AGENTS.md，确认当前分支、型号、编译宏和用户要求的协议版本。
   优先复用项目已有模板和输出位置；没有约定时写入
   `docs/modbus/<Manufacturer>/<Device>.json`。型号/协议存在无法区分的多个候选时询问，
   可以先整理已确认的公共寄存器，但不要将不同型号、产测模式或版本混成同一模板。
2. 用 `rg` 查找 Modbus 功能码处理、地址分发、寄存器映射、序列化函数和协议文档。
   从读请求入口追踪地址变换与最终返回字节，核实地址、长度、符号、字序、缩放、单位、
   枚举、位定义和访问条件。写入处理可辅助确认权限，但不能代替读取映射。
   C 变量的内存类型不一定等于线上类型。以所选构建的实际实现为准，明确记录与文档的冲突。
3. 读取 [references/template-format.md](references/template-format.md)，按该格式生成 UTF-8 JSON。
   一行表示一个有意义的字段；连续多寄存器值保持完整，不跨未定义地址拼接。
   保留地址空洞，不为“完整覆盖”杜撰保留寄存器。单独列出缺少证据而未纳入的字段。
4. 在相邻的 `<Device>.sources.md` 中记录目标分支/提交（以及有关的未提交修改）、构建型号、
   来源文件和行号/文档页码、地址基准、换算公式和关键解码例子。
   大型映射可按地址段记录共同证据，特殊枚举、位域、字序和偏移另列。
   连接参数未知时可省略可选参数并说明仍需配置；不要把应用默认值写成设备已确认默认值。
5. 运行技能自带校验器（把 `<skill-dir>` 替换为本 SKILL.md 所在目录）：

   ```bash
   python3 <skill-dir>/scripts/validate_template.py <output.json>
   ```

   它只做静态格式和范围检查，不能证明寄存器语义或设备通信正确。
   对照来源复核至少一个有符号/缩放值、多字寄存器和枚举/位域（若存在）。
   若当前环境有 Modbus Connector 源码，可进一步用 `templates.parse_template` 和
   `flutter_catalog.flutter_state` 检查加载；不要为此强制安装 GUI 或连接设备。
6. 交付文件路径、行数/地址范围、来源版本、校验结果和仍未确认的信息。
   不把格式校验描述为实机验证。

## 边界与更新

- 用户要求更新现有模板时，保留已有名称、顺序和手工标注；仅修改有依据的字段，说明增删。
- 生成的是 `name/connection/registers` 模板，不是 Flutter 原生 workspace、Qt 多标签设置，
  也不是带 UUID/versions 的个人模板历史。需要这些格式时单独按对应导入接口转换。
- 只生成请求的文件。不要修改用户全局设置、云缓存或发布模板，也不要执行连接、写寄存器、
  烧录等操作来“验证”生成结果；这些需要另有明确任务授权。
